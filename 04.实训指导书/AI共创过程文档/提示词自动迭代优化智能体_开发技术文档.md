### 2.1 总体架构

系统采用前后端分离的 B/S 架构，分为三层：前端展示层、后端服务层、数据与AI能力层。

└───────────────────────────────┬────────────────────────────────────┘

## 五、核心技术实现

### 5.1 迭代编排（LangGraph）

优化循环以状态图形式编排，核心节点：

```
                 ┌──────────┐
                 │ 生成变体  │  ← 基于当前最优 + 失败案例
                 └────┬─────┘
                      ▼
                 ┌──────────┐
                 │ 执行任务  │  ← 变体 × 用例，并发 + 重试
                 └────┬─────┘
                      ▼
                 ┌──────────┐
                 │ 质量评估  │  ← 自动指标 + 评审打分加权
                 └────┬─────┘
                      ▼
                 ┌──────────┐
                 │ 择优更新  │  ← 更新 best_prompt / best_score
                 └────┬─────┘
                      ▼
                 ┌──────────┐
                 │ 终止判断  │──达标/收敛/最大轮次──→ END
                 └────┬─────┘
                      │ 未终止
                      └──────→ 回到「生成变体」(下一轮)
```

- **状态对象**（State）：`task_id`、`current_round`、`best_prompt`、`best_score`、`variants`、`stagnant_rounds`、`fail_cases`、`stop_flag`。
- **终止判断**：设置了 `target_score` 时以 `best_score >= target_score` 为准；未设置时，连续 `stagnant_rounds`（默认 2 轮）每轮最优得分无提升判定收敛，或 `current_round >= max_rounds`（默认 5，可配置 1/2/3/5）。
- **初始提示词**：任务未填写 `initial_prompt` 时，首轮前调用大模型按 `description`、`objective`、`criteria` 自动生成并落库为第 0 版。
- **停止/冻结**：在节点间检查 `stop_flag`，用户停止时在图入口让出控制权并落库当前结果，保留 `current_round`。
- **断点续跑**：`stopped` 任务重启时以 `current_round` 为起点继续下一轮，已完成的用例执行与评估结果复用不重算；`completed` 任务重启则从第 1 轮重新开始。

### 5.2 变体生成策略

调用大模型基于「当前最优提示词 + 上一轮失败案例描述」生成 `variants_per_round` 个变体，策略标签包括：

| 策略 | 做法 |
|------|------|
| failure_inject | 把失败用例或低分反馈作为反例写入提示词 |
| rewrite | 结构调整提示词的分层与约束顺序 |
| constraint | 把隐式要求显式化为硬性规则 |

### 5.3 批量执行与重试

- 每个变体对全部用例并发执行，并发数受配置 `concurrency` 限制。
- 对超时 / 限流 / 接口错误自动重试（默认 2 次），重试仍败则标记 `failed` 并记录 `error_reason`。
- 执行结果（`model_output`、`outcome`）写入 `eval_results` 落库，保证可复现。

### 5.4 自动指标计算

| 指标 | 工具 | 说明 |
|------|------|------|
| BLEU | NLTK | n-gram 重叠，输出 vs 参考输出 |
| ROUGE | rouge 库 | ROUGE-L 等，摘要/生成任务 |
| 关键词命中 | 自实现 | 校验输出是否含必需关键词 |
| 格式合规 | 自实现 | 校验 JSON / 列表 / 长度等结构 |

各指标归一化到 0-100。无参考输出时自动跳过依赖参考的指标。

### 5.5 评审打分

评审打分大模型按任务的 `criteria` 对每个变体在各用例上的输出给出 1-10 分与理由。评审模型可独立配置（任务级 `judge_model`），缺省沿用执行模型。评审理由留痕，供报告与人工抽检使用。

人工抽检通道：用户可对任意评估记录提交人工评分与备注，写入 `eval_results.manual_score`，用于校验自动评审与人工评分的一致率并作为权重校准确参考。

### 5.6 综合得分合成

```
single_case_total = w_auto × auto_metric_score + w_judge × judge_score_0to100
variant_total     = mean( single_case_total over all cases )
```

默认 `w_auto=0.5`、`w_judge=0.5`；无参考输出用例 `w_auto` 降为 0。权重由任务配置（`auto_weight`、`judge_weight`）决定。

### 5.7 LLM 客户端封装

统一 `llm/client.py` 封装 OpenAI 兼容调用，支持：

- 指定模型、温控、最大 token；
- 结构化输出（JSON 模式）用于评审理由与变体生成；
- 超时与重试（重试集包含 `httpx.HTTPStatusError`：仅 5xx/429 重试，非 429 的 4xx 立即抛出，429 使用更重的退避策略）；空消息异常改写为携带类型名称的 `RuntimeError`；敏感字段脱敏。

### 5.8 RAG 检索与评测

- **双模式检索**：知识块存储 `embedding` 字段——嵌入模型可用时存 `[float,...]` 向量（OpenAI 兼容 embeddings 接口），否则存 `{"ngrams":{词:频次}}` 词法指纹（纯本地、无外部依赖）。检索按库的 `embed_model` 自动选择向量相似度或词法指纹打分。
- **查询侧容错**：查询嵌入失败（`qvec=None`）时返回空列表，而非全 0 得分的任意命中，避免注入错误上下文。
- **原子计数**：`doc_count` / `chunk_count` 更新用 SQL 原子自增（`update ... values(doc_count=KnowledgeBase.doc_count+1)`），禁止 ORM 对象 `+=` 后 commit，防止并发上传同库丢更新。
- **评测指标**：`rag_service.evaluate` 对每个用例做「检索 → 注入上下文生成 → 评估」，输出两项 0-100 评分：来源支撑度（答案与检索来源的关联程度）与忠实度（答案对来源内容的忠实程度）。
- **一键导入**：`import-corpus` 仅接受配置目录 `RAG_CORPUS_DIR`，不接受任意用户路径，防止任意文件读取漏洞。

### 5.9 在线服务（端点发布与调用）

- 端点把任务最优/冻结提示词快照 + 执行模型固化为可对外调用的 HTTP 接口；密钥 `sk-` 前缀 urllib-safe 随机生成，鉴权用 HMAC 恒定时间比较防时序攻击，支持轮换（旧密钥立即失效、历史日志保留）。
- **限流**：按端点维度默认 60 次/分钟（内存滑动窗口），超限返回 429；调用计数用 SQL 原子自增。
- **日志与统计**：每次调用写 `endpoint_call_logs`（输入、输出、状态、耗时），统计接口用 SQL 聚合函数（`COUNT`/`SUM`）而非内存计算。
- **调用入口**：`POST /endpoints/{id}/invoke` 仅校验 `X-Api-Key`，不依赖 JWT，可被 curl / Postman / 程序代码直接调用。

### 5.10 模型评测平台

- 一次评测运行在多个模型 × 多个用例上执行同一提示词快照，结果写入 `benchmark_results`，形成「模型 × 用例」得分矩阵。
- 评审分做横向归一化（1-10）后按模型聚合平均分，`best_model` = 平均分最高的模型（推荐模型）。
- 评测异步执行（复用 executor 与 judge_service），前端轮询 `status` 直至 `completed`，可导出矩阵报告。

### 5.11 多步骤工作流

- **链式执行**：`workflow_executor.py` 按 `seq` 顺序执行步骤，指令模板支持 `{{input}}` 与 `{{stepN.out}}` 占位符，推理前用已完成变量集插值；每用例记录 `step_trace` 供报告展示。
- **基线对照**：`run_baseline=1` 时同时跑单 prompt 基线，输出 `baseline_avg_score` 与工作流 `avg_score` 对比，量化多步编排收益。
- **步骤优化**：`workflow_step_optimizer.py` 复用优化器的变体生成与链式评测，对指定步骤指令做多轮贪心迭代（轮次可配置 1/2/3/5），每轮生成变体→整链评测→择优，连续两轮无提升提前终止，完成后回写该步骤 `prompt_template`。
- **并发控制**：同一工作流并发发起执行由后端按工作流粒度的 `asyncio.Lock` 串行化「运行计数 + 创建运行」临界区，防止重复运行；`_start_locks` 字典实现定期清理，防止长运行服务内存缓慢增长。
- **数据隔离**：工作流运行与步骤优化数据必须通过 `workflow_id` 关联过滤 `Workflow.user_id`，防止跨租户泄露。

### 5.12 报告分享

- 为「模型评测 / 工作流步骤优化 / 任务迭代」三类报告生成 token 分享链接：`report_type + target_id` 定位报告实体，`token` 为 URL 访问凭证（唯一索引）。
- 有效期：`expires_at`（ISO 时间戳），空 = 永久；撤销置 `status=revoked` 后公开访问立即失效。
- 公开只读：`/public/reports/{token}/data` 免登录返回只读载荷，仅原子自增 `view_count`，不暴露任何编辑能力。

### 5.13 仪表盘统计

- `dashboard_service.py` 使用 SQL 聚合函数（`COUNT`/`SUM`）统计资产总览（任务、用例、迭代、知识库、端点、工作流、分享、调用量），禁止内存计算。
- `get_trend(days)` 包含窗口起始过滤，返回指定天数（含当天）的数据；`search_versions` 的 `total` 返回实际匹配计数（`q.count()`）而非被 limit 截断的 `len(items)`。

## 六、认证与安全

1. **认证**：JWT（Bearer token）无状态认证，24 小时有效期；JWT 密钥使用 `secrets.token_urlsafe(64)` 生成，部署版出厂不带有效密钥（`.env` 为空占位并在启动时强制提示填写）；密码使用 bcrypt 哈希。
2. **登录防暴力破解**：登录接口按「IP + 邮箱」失败计数，连续 5 次失败锁定 15 分钟，锁定期间返回 429。
3. **数据隔离**：所有业务接口经 `get_current_user` 注入当前用户，服务内校验资源 `user_id` 属主；工作流等扩展模块经 `workflow_id` 关联过滤用户；管理员接口仅 `role=admin` 可访问（不能禁用自身）。
4. **在线调用安全**：`X-Api-Key` 鉴权（HMAC 恒定时间比较）+ 按端点限流（60 次/分钟），防止密钥泄露后无限刷调用。
5. **密钥管理**：包含 API 密钥的 `.env` 绝不提交 git（全项目 `.gitignore` 含 `.env`），提供 `.env.example` 占位。
6. **前端安全**：登录态由后端 HttpOnly Cookie 管理（前端不存 token），配合 CSP 头，降低 XSS 场景下的凭证窃取风险。
7. **路由兜底**：未匹配的 `/api/v1/xxx` 路径返回 JSON 404 而非 `index.html`，避免前端排错混淆。
8. **脱敏**：调用外部 LLM 前对提示词中的敏感字段做占位替换。
9. **合规标识**：对 AI 生成内容打标与显著标识（响应头/界面角标）。

## 七、开发规范

1. **代码注释**：关键函数含中文 docstring（参数、返回值、异常），方便人工审阅；每个代码段必须有中文注释解释功能，并提供足够的中文说明供人工审核。
2. **后端规范**：
   - Service 层负责业务逻辑，Endpoint 层只做参数接入与响应组装。
   - 使用 Pydantic schema 做请求/响应校验，不直接暴露 ORM 对象。
   - 错误统一抛业务异常，由全局 handler 转 JSON 响应（code/message/data）。
   - 分页参数边界检查：`page ≥ 1`、`10 ≤ page_size ≤ 100`；统计数据用 SQL 聚合。
   - 并发写（知识库计数、端点计数、分享访问数）必须用 SQL 原子自增。
3. **前端规范**：
   - TypeScript 严格模式，接口返回类型与 `src/types` 对齐。
   - API 调用统一走 `src/api` 的 Axios 实例（统一错误处理，401 兜底清本地并跳登录）。
   - 页面状态用 Zustand；表单跨步骤切换用 `display:none` 保留 DOM 状态。
4. **配置管理**：敏感配置（LLM key、JWT Secret）存 `.env`，提供 `.env.example`；部署包 `.env` 使用空占位并强制启动提示。
5. **测试**：后端 pytest 覆盖核心服务与全部模块（13 文件 91 项，语句覆盖率 84%）；前端 vitest 覆盖工具函数；关键模块（security/models/schemas/templates/dashboard）要求 100% 覆盖。

## 九、风险与对策

| 风险 | 对策 |
|------|------|
| LLM 限流/不可用 | 超时 + 重试 + 失败隔离，不阻塞其他用例 |
| 过拟合测试用例 | 验证集/测试集隔离，验证集择优、测试集验证 |
| 单轮耗时长 | 并发执行 + 变体/用例规模可配 + 分批处理 |
| 自动指标与人工偏差 | 保留人工抽检通道，报告含评审理由供校准 |
| 并发上传 / 并发调用丢计数 | 计数一律 SQL 原子自增，严禁 ORM 对象 += 后 commit |
| 密钥泄露 / 被刷调用 | `.env` 不入库、JWT 强随机、在线调用 HMAC 鉴权 + 限流、部署版空占位强制填写 |
| 并发工作流重复运行 | 工作流粒度 asyncio.Lock 串行化运行创建临界区 |
| 跨租户数据泄露 | 所有资源访问同时校验 task_id 与 user_id 归属 |
