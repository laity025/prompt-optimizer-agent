# 提示词自动迭代优化智能体 · 前端模块功能解析

> **解析依据**：`prompt-evolver-ui/pages/` 的 12 个界面原型（登录、任务列表、创建任务三步、迭代看板四页、管理两页），
> 与 `01.code/prompt_optimizer/frontend/src` 的实际实现（14 个路由、9 个接口模块）逐页比对。
>
> **口径**：一个「模块」= 侧边栏一个一级入口（或一个独立路由页）。
> 每节按同一套路写：**入口 → 界面上有什么 → 能做什么 → 作用（解决什么问题）**。

## 1. 登录 / 注册

**入口**：独立布局（无侧边栏），路由 `/login`。

**界面上有什么**

左侧是品牌区：`PROMPT EVOLVER · v2.0`，主标语「把上千次试错压缩成一次迭代」，英文小标 `Auto Prompt Optimization`。
右侧是表单区：登录时是「邮箱 + 密码」；切到注册再增一个「确认密码」和选填的姓名（提示「选填，将显示在侧边栏」）。
按钮文案随状态变化：`登录 · Enter` / `登录中` / `注册并自动登录` / `注册中`。
底部有一行约定说明：「登录即代表同意《迭代服务条款》与数据仅用于优化任务的约定」。

**能做什么**

- 登录、注册（注册成功即自动登录，无需二次登录）；
- 前端做四类校验并给出具体提示：邮箱格式、密码至少 6 位、两次密码不一致、邮箱已被注册；
- 登录失败提示「邮箱或密码错误，请重试。」——**不区分「邮箱不存在」和「密码错误」**，避免被用来探测哪些邮箱已注册。

**作用**

这是整个系统的会话入口，也是**权限模型的第一道口子**：
登录成功后凭证由后端写入 **HttpOnly Cookie**，前端本地只保存用户信息、不存 token（`App.tsx` 顶部注释写明了这个设计）。
未登录访问任何内页会被路由守卫重定向回登录页，并记录来源地址，登录后跳回原目标。
会话过期由后端 `401` 兜底，前端统一拦截后清理本地状态并跳登录——这样即使有人翻到了本地存储，也拿不到可用的凭证。

## 2. 资产门户（Dashboard）

**入口**：侧边栏第一项「资产门户」，路由 `/dashboard`。

**界面上有什么**

顶部是 **8 个指标卡**：任务、用例、Prompt 版本、模型评测、工作流、知识库、在线端点、累计调用。
下面五个区块依次是：

| 区块 | 内容 |
|---|---|
| 任务类型分布 | 饼图，按文本生成 / 摘要 / 信息抽取 / 代码生成 / 自定义拆分 |
| 近 N 天活动趋势 | 折线，可切 **30 / 60 / 90 天**；含端点调用、工作流运行、步骤优化三类活动 |
| 任务资产 | 表格：任务、类型、状态、用例、版本、评测、工作流、最优分、迭代进度、更新时间；支持按任务名搜索 |
| 模型调用统计 | 模型、调用次数、成功率、平均耗时（无调用时显示「暂无端点调用」） |
| Prompt 版本库 | 按任务筛选 + 搜索 prompt 内容或任务名，列出历史版本 |

**能做什么**

只读为主：看总量、看分布、看趋势、搜版本。没有「在这里改东西」的入口，所有操作都跳回各自的模块。

**作用**

这是**「家底」视图**，回答的是管理者视角的三个问题：

1. **积累了多少**——任务、用例、Prompt 版本、知识库、端点各有多少；
2. **用起来了没有**——端点调用了多少次、成功率多少、平均耗时多少；
3. **成果在哪**——按任务名或提示词内容一搜，历史版本立刻能找到。

它把一个很容易变乱的现实问题摆到台面上：**调了很久的提示词，如果散在各处、没人知道哪个版本最好，就等于没有资产**。资产门户把这些沉淀物统一清点，让「可冻结、可回退、可分享」从口号变成看得见的数字。

## 3. 任务列表

**入口**：侧边栏「任务列表」，路由 `/tasks`。

**界面上有什么**

- 顶部筛选：**全部 / 待运行 / 运行中 / 已完成 / 已停止 / 失败**（原型里带计数，如「全部(6)」「运行中(1)」）；
- 右上「新建任务」按钮；
- 搜索框：「按任务名搜索，回车确认」；
- 任务卡片列表，每条显示：序号、当前得分（`91.2 分/100`）、任务名、类型标签、状态、轮次进度（`10/10 轮`、`03/10`）、用例数、更新时间；
- 操作：进入任务、删除任务（提示「将级联删除其全部用例与迭代数据」）；
- 空状态：「还没有任务，从创建第一个优化任务开始」，并给一个「创建第一个任务」的按钮。

**能做什么**

按状态筛、按名字搜、进任务、删任务、新建任务。

**作用**

**任务的总控台**。对使用者来说，这里是每天的第一站，一眼要能回答：哪个跑完了、哪个还在跑、哪个卡住了、哪个我该停掉。

两个设计细节值得注意：
一是**筛选维度用的是运行状态而不是时间**，因为这里的「待办」天然就是状态驱动的——跑完的去拿报告，跑着的等结果，停掉的考虑要不要续跑；
二是**删除被明确标注为级联删除**，把「删掉任务也会删掉它的用例和迭代记录」写在确认框里，避免误删之后才发现历史数据没了。

## 4. 创建任务（三步向导）

**入口**：侧边栏「创建任务」（可展开 5 个任务类型子项），路由 `/tasks/new?type=xxx`。

**界面上有什么**

顶部三步进度条：**01 基础信息 / 02 测试用例 / 03 确认创建**，右下角按钮在「下一步」与「创建并立即运行」之间变化。

### 第一步 · 基础信息

| 区域 | 字段与说明 |
|---|---|
| 选择任务类型 | 五个模板卡，各带英文小标与适用说明：文本生成（营销文案、对话话术、内容创作）、文本摘要（长文压缩、要点提炼）、信息抽取（实体、字段与结构化信息提取）、代码生成（函数、脚本与代码补全）、自定义（特殊场景，自定义评分维度） |
| 任务名称 | 限 50 字，带字数计数（如 `9/50`），例：电商客服话术优化 |
| 任务描述 | 清晰描述需要优化提示词的生成任务 |
| 优化目标 | 例：提升互动转化，收藏率 ≥ 8%；事实零偏差，禁止违禁极限词 |
| 评分标准 | 按维度给权重，例：吸引力 30% / 相关性 25% / 信息量 20% / 合规性 15% / 语言风格 10% |
| 初始提示词（可选） | 留空则由系统在首轮自动生成 V0 基线 |
| 运行参数 | 执行模型、评审模型（可「沿用执行模型」）、自动指标权重、评审打分权重、每轮变体数（2–8）、最大轮次（1–30）、并发数、收敛判定轮数、目标分数（可选） |
| 知识库检索 | 开关 + 绑定知识库（显示该库块数），开启后评测时自动检索注入上下文 |

关于**目标分数**，界面给了一句很关键的说明：留空则不含达标线，任务会持续迭代，直到连续 N 轮无提升或达到最大轮次；填写后达到该分即提前完成。**收敛判定轮数**默认「连续 3 轮提升不足 0.5 分判定收敛」。

### 第二步 · 测试用例

每条用例三个字段：**输入（必填）、参考输出（可选）、关键词（逗号分隔，可选）**。
支持「添加用例」逐条录入，也支持「批量导入」——拖拽 JSON / CSV 文件到此处（单文件 ≤ 2MB，UTF-8），并可直接**下载 JSON / CSV 模板**。
导入说明写在界面上：`字段 input 必填，expected、keywords 选填；关键词使用英文逗号分隔；文件编码需为 UTF-8`。
导入后立刻反馈结果：「解析成功 5 条 / 失败 0 条」。另有「清空」及二次确认。

### 第三步 · 确认创建

上半是**任务摘要**（类型、名称、用例数量、执行模型、评审模型、指标权重、每轮变体数、最大轮次、并发数、收敛规则），
下半是**用例预览**（前两条的输入与关键词，其余折叠为「…另有 3 条用例」）。
底部两条准备提示：「创建后将自动进入迭代看板，可随时开始第一轮迭代」「预计单轮耗时 2–4 分钟，可中途停止，已产生的版本会保留」。
最后两个按钮：**仅创建** / **创建并立即运行**。

**能做什么**

选模板 → 填目标与评分标准 → 配运行参数 → 录入或导入用例 → 复核摘要 → 创建（可选立即开跑）。

**作用**

这一步是**整个系统里唯一需要人认真思考的地方**，因为它在定义「什么叫更好」：

- **优化目标**决定方向，**评分标准**决定尺度，**用例集**决定考卷。
- 这三样一旦定下来，后面 10 轮迭代、几百分的评分、几十个版本的取舍，全部是自动推导出来的结果。

换句话说，**提示词优化的质量上限，在这一页就被锁定了**。系统能做的只是把这份标准执行得比人更彻底、更不知疲倦。
另外两个设计是刻意的：**初始提示词可以留空**（让系统自己生成 V0 基线，避免人被自己的旧版本锚住）；**评分标准按维度配权重**（把「我觉得这个好」拆成可加总的分项，这是自动评分能与人工判断对齐的前提）。

## 5. 任务详情 · 迭代看板（产品核心）

**入口**：任务列表点进任一任务，路由 `/tasks/:id`。

**页头**：返回任务列表、任务名、类型标签、状态、用例数、`ROUND / 轮次`。
**四个页签**：`01 概览` / `02 迭代过程` / `03 用例集` / `04 报告`。
**页头操作**：开始迭代 / 停止迭代（「已产生的结果将被保留」）/ 继续迭代 / 重新迭代（「将清空上一轮的迭代记录，从最初的初始提示词重新开始」）。

### 5.1 概览

四个指标：**当前最优**（91.2，附「▲ 较初始 +18.4」）、**初始得分**（72.8，标 `V0 基线`）、**已用轮次**（`10 / 10`，标 `max 10 · 已收敛`）、**用例通过**（`22 / 24`，注「2 条未达预期」）。

下面是两块内容：
一是**当前最优提示词**（带 `91.2 分` 徽标），完整展示 `# 角色 / # 任务 / # 要求 / # 输出` 四段结构；
二是**初始与最优差异对比**——左边 V0（72.8 分），右边 V10（91.2 分），差异逐条列出。

底部操作：**导出报告** / **冻结版本** / **回退初始 V0**（提示「回退后 V1–V10 记录仍保留，当前编辑版本将被替换为 V0」）。
另有状态提示区：任务就绪（开始首轮迭代）、已停止（可点「继续迭代」断点续跑）、失败（显示 `last_error`）。

### 5.2 迭代过程

上半是**得分曲线**：横轴轮次、纵轴综合得分，标注**目标分 90**，收敛后打上 `DONE` 标记，并给出三个总结数：**最终得分 91.2 / 峰值提升 +18.4 / 总耗时 32 分钟**，旁边注明「人工抽检校准」。

下半是**每轮版本列表**（Round 01 → Round 10），每轮的结构是：

- **轮次汇总**：该轮得分（74.2 基线、76.8 ▲+2.6、79.1 ▲+2.3 …… 91.2）、时间戳、`回退到此轮` 按钮；
- **该轮的 4 个变体**（V1.1–V1.4）：每个变体给 **自动分 / 评审分**（如 `自动 75.4 / 评审 73.0`）和一句**自然语言的评审理由**；
- 该轮胜出的变体被标记，最终轮采纳的 V10.1 标「已采纳」。

评审理由是这个模块最有说服力的部分，它是具体的一句话人话，例如：

> 「礼貌但空泛，缺少政策引用与明确下一步。」
> 「回答方向正确，但未给出可执行的处理路径。」
> 「出现超出政策的补偿承诺，风险较高。」
> 「角色设定统一了客服口吻，专业感提升。」
> 「首次越过目标分 90，JSON 合法率 96%。」

**人工抽检**是一个弹窗：以「变体 × 用例」为行，列出用例、自动指标、评审理由摘要、**人工评分（1–10）**、备注，逐条提交。

### 5.3 用例集

任务所有的测试用例：**输入 / 参考输出 / 关键词 / 操作**，逐条可删（二次确认），可继续「添加用例」（输入必填，参考输出与关键词可选），也可**导入 JSON / CSV**（返回「导入成功 N 条，失败 M 条」）。
代码生成类任务额外提供「单元测试（代码生成可选）」一栏，填 JSON 字符串。

### 5.4 报告

完整报告页，包含：

| 区块 | 内容 |
|---|---|
| 报告头 | 轮次 `10 / 10`、用例 `24 条`、生成时间 |
| 最终最优提示词 | 全文 + `91.2 分` + 「较初始 +18.4」 |
| 版本差异对比 | `V0 → V10` 的逐条 diff：**删除**了什么（「要礼貌，专业，尽量解决问题。」——泛化要求，无角色、无结构、无政策依据）、**新增**了角色设定、长度约束、三段式结构、政策条款引用、结构化输出 |
| 各轮评分理由汇总 | R01–R10 每轮一句话总结（如 R07「压缩冗余措辞，平均回复字数由 156 降至 132」） |
| 优化建议 | 系统给的 4 条后续建议，例：补充售后异常场景用例；大促期间把每轮变体数由 4 提到 6；建议月度用异源模型校准评审；对 JSON 输出加 schema 强校验 |
| 报告信息 | 生成人、**评审一致率 92%**、执行模型 `deepseek-v4-flash` / 评审模型 `gpt-5-mini` |
| 导出 | **导出 Markdown / 导出 JSON**、分享 |

**作用**

四个页签其实就是四个问题，一页回答一个：

| 页签 | 回答的问题 | 给谁看 |
|---|---|---|
| 概览 | **结果怎么样？** | 自己先看结论，决定要不要继续 |
| 迭代过程 | **为什么能到这一步？** | 复核过程是否可信、哪一轮走了弯路 |
| 用例集 | **题目对不对？** | 分数不理想时，先怀疑考卷 |
| 报告 | **怎么把这个结论交出去？** | 评审、同事、外部 |

这个模块真正的作用，是把「提示词优化」从**一次性手感**变成**可复核的过程**。
三个细节支撑了这一点：**每轮可回退**（走错能退，不怕试）、**每个变体都有评审理由**（分数不是黑箱）、**人工抽检可介入打分**（自动评分跑偏时有人工校准通道）。

## 6. 模型评测

**入口**：侧边栏「模型评测」，路由 `/benchmarks`。

**界面上有什么**

- 选择要评测的任务；
- 选择**评测提示词的三种模式**：`当前最优` / `初始提示词` / `自定义`（选自定义时必须填评测提示词）；
- 多选参与对比的模型（例：DeepSeek-V4-Flash）；
- 评测名称（留空自动命名）；
- 记录列表：评测名称、所属任务、对比模型、状态（评测中 / 已完成 / 失败）、**最优模型**（出现同分时显示「并列 N 个模型」）、最优得分、发起时间、操作；
- 操作：查看结果、分享评测报告、导出；
- 空状态与校验提示：「请先选择需要进行评测的任务」「请至少选择一个参与对比的模型」「自定义模式下请填写评测提示词」「评测已启动，完成后将自动刷新结果」。

**能做什么**

同一批用例 + 同一份提示词，横向跑多个模型，输出各模型平均得分与最优推荐；能导出报告、能分享。

**作用**

它回答一个实际工作中一定会遇到的问题：**这套提示词，用哪个模型效果最好？**

不靠印象、不靠别人说，用**同一份考卷**跑一遍就有结论。三个设计点保证结论可信：

1. **三种提示词模式**——可以对比「最优提示词在不同模型上的表现」，也可以看「同一个模型拿到不同提示词的差异」，还能用自定义提示词做第三方基准；
2. **沿用同一套打分口径**——不同模型的分才有可比性；
3. **记录可留存、可分享**——决策有据可查，不是一次性的实验。

## 7. 在线服务

**入口**：侧边栏「在线服务」，路由 `/services`。

**界面上有什么**

- **创建在线服务**：选择要上线的任务 → 选择版本（`当前最优` / `初始提示词`，已冻结的会标「（已冻结）」）→ 名称（留空自动命名）→ 用途说明（可选）→ 模型（留空则用任务配置的执行模型）；
- 服务列表：名称与状态（**已启用 / 已停用**）、操作（**启用 / 停用 / 轮换密钥 / 删除**）；
- 删除确认：「删除后不可恢复，确认删除该在线服务？」；
- 服务详情：**调用统计**（累计调用次数等）；**在线测试**（输入测试内容 → 调用 → 显示「你的输入」与输出；失败时提示「调用失败，请查看下方日志/错误提示」）；
- **调用日志**：时间、状态（成功 / 失败）、耗时、输入、输出/错误；
- 提示反馈：`在线服务创建成功`、`密钥已轮换`、`已启用`、`已停用`、`已删除`、`已复制`。

**能做什么**

把某个任务的某个提示词版本发布成在线接口；启停、轮换密钥、删除；用界面直接试调用；查调用日志与统计。

**作用**

这一步是产品性质的转变：**从「自己用的工具」变成「别人能用的服务」。**

提示词优化完之后，最常见的下一步是「让业务系统用起来」。如果没有这个模块，做法通常是把提示词复制出去、由开发重新写一版接口——**两边从此各走各的，线上跑的和系统里评测的再也不是同一个东西**。

在线服务把最后一公里接上了：发布的永远是**系统里评测过的那个版本**（当前最优或已冻结），调用方拿密钥直接调、不用登录，密钥能轮换、服务能停用、每次调用都有日志。
两个细节对应现实风险：**版本选择锁定在「最优 / 已冻结」**，防止误上线一个中间版本；**密钥可轮换**，泄露了能立刻作废，而不是只能删服务。

## 8. 知识库

**入口**：侧边栏「知识库」，路由 `/knowledge`。

**界面上有什么**

- **我的知识库**列表：名称、用途说明、块数（如「（N 块）」）、创建时间、操作（删除，提示「删除后语料与检索块一并清除，确认？」）；
- **创建知识库**：名称 + 用途说明（可选）；
- **上传语料**：粘贴或输入语料内容，提交后提示「入库成功，切分为 N 个检索块」（系统自动分块并建索引）；
- **示例语料导入**：一键导入内置示例，返回「示例语料导入完成：成功 N / 共 M」；
- **两个工作区**：
  - **检索**：两种模式可切换——**向量检索**（显示当前 embedding 模型）与**词法检索（无外部依赖）**；输入问题查看命中的块（占位提示：如「前端使用什么技术栈？」），无结果时显示「暂无检索结果」；
  - **评测**：输入问题 → 检索后生成答案并**评估忠实度**（占位提示：如「本项目整体架构？」）。

**能做什么**

建库、灌语料（逐条或批量或一键示例）、切检索模式、试检索、做忠实度评测、删库。

**作用**

解决**模型「不知道」的问题**——也就是幻觉的根源之一。

任务本身可以开启 RAG：开启并把知识库绑到任务上之后，评测时会自动检索相关片段注入上下文（创建任务的第一步里就有这个开关，并显示该库的块数）。于是模型回答的依据从「它记住的」变成「你给的」，事实类用例的通过率会明显上升。

**两条检索路径是这个模块设计上最务实的一点**：优先用语义向量，**向量模型不可用时自动降级为词法检索**，且明确标注「无外部依赖」。
这意味着——**没有部署任何向量模型，知识库照样能用**。对一个要交付、要部署到别人机器上的系统来说，这个降级路径的价值远大于多一个高级功能。

**忠实度评测**则是配套的度量：回答有没有原文支撑，给 0–100 分。有了它，「加了知识库到底有没有变好」才是一个能回答的问题。

## 9. 工作流

**入口**：路由 `/workflows`（⚠️ 见文末「发现的问题」——侧边栏暂无入口）。

**界面上有什么**

- 选择要编排工作流的任务（未选时提示「请先选择一个任务」）；
- **步骤编排区**：每个步骤三栏——步骤名（如「翻译→润色」）、模型（留空用默认）、**指令模板**（占位提示：`请把下面内容翻译成英文：{{input}}`）；可继续「步骤N」追加；校验「至少保留一个含指令的步骤」；
- **对照选项**：「仅评测工作流」/ 或将同时以任务最优 / 初始 prompt 跑单次对照（即**整链 vs 单条**的对比）；
- 工作流列表：名称、描述、状态、操作（编辑 / 运行 / 删除，删除有二次确认）；
- **评测报告**：各步骤得分与整链分，运行时提示「评测运行中，正在生成报告…」；
- **步骤优化**：选择某一步 → 开始优化 → 显示进度与结果（`{原分} → 最优 N 分`、**提升 X 分**、`无提升`、`本轮无有效变体`、与对照的`优于/逊于 N 分`）；优化记录可留存，暂无时显示「暂无优化记录 / 暂无历史」；
- 分享步骤优化报告。

**能做什么**

把一个任务拆成多步串联的工作流，每步用自己的指令模板，用 `{{input}}` / `{{stepN.out}}` 在步骤间传参；
整链一起评测；**也可以只针对某一步做多轮自动优化，按整链得分择优回写**；并能与「单条提示词」跑法做对照。

**作用**

它解决的是**一句话提示词搞不定的任务**。

现实里的复杂任务常常是「先翻译、再润色、最后校验格式」这种链条。硬塞进一个提示词，会出现典型的互相干扰：改了润色风格，翻译准确性掉了；要求格式严格，内容就缩水。

工作流把任务拆开之后，带来两个好处：

1. **每一步可以单独优化、单独定位问题**——分低了立刻知道是哪一步拖的；
2. **能验证「拆开值不值」**——通过「整链 vs 单条」对照，用分数回答「多步是不是真的比一句提示词好」。

## 10. 分享中心 与 公开报告页

**入口**：分享生成入口在各报告页的「分享」按钮；分享中心路由 `/shares`；公开页路由 `/share/:token`（免登录）。

**界面上有什么**

**分享弹窗（ShareModal）**：选有效期——**永久 / 1 小时 / 12 小时 / 24 小时 / 7 天 / 30 天**，生成后一键复制链接（有「已复制」与「复制失败，请手动选择链接复制」两种反馈）。

**分享中心**：三个类型页签——**评测对比 / 步骤优化 / 任务迭代**；列表含报告名、**访问次数**、有效期、状态（**生效中 / 已撤销**）、创建时间、操作（复制公开访问链接 / 撤销分享）；
撤销有二次确认：「撤销后该链接将立即失效，确定？」；空状态提示「还没有分享记录。进入评测/优化/任务报告页点击「分享」即可生成链接」。

**公开报告页**（外部人视角，只读）：顶部显示报告类型与「· 有效期至 xxxx-xx-xx」；按类型自适应渲染——多模型对比评测显示各模型平均得分、最优模型、得分矩阵（用例 × 模型）；工作流步骤优化显示基准整链分 / 优化后整链分 / 提升、指令前后对照（优化前 / 优化后）、各轮变体、最优提示词；任务迭代报告显示迭代得分曲线、每轮评审总结、优化建议。链接失效时提示：「该分享链接不存在、已被撤销或已过期」。

**能做什么**

从任何一份报告一键生成带有效期的公开链接；在分享中心统一查看访问量、复制、撤销。

**作用**

把成果**给别人看**，而不用给别人开账号。

答辩、汇报、跨部门协作里最常见的需求就是这个：「把这份评测结果发给对方」。开账号涉及人员管理，截图和导出又不方便更新。分享链接一次解决三个问题：**免登录可看**（对方零成本）、**可设有效期**（临时评审用短期、对外材料用长期）、**可随时撤销**（发错了能收回，且带访问次数可判断对方是否看过）。

## 11. 用户管理（管理员）

**入口**：侧边栏 `ADMIN · 管理员` 分组下「用户管理」，路由 `/admin/users`，非管理员访问会被重定向。

**界面上有什么**

- 「邀请成员」按钮；筛选页签：**全部 / 普通用户 / 管理员**（带计数）；
- 表格列：**邮箱、姓名、角色、账号状态、创建时间、操作**；
- 操作：**设为管理员 / 取消管理员**、**禁用 / 启用**（当前账号显示「当前账号」，不可对自己操作，会提示「不能对自身账号执行启停操作」）；

**能做什么**

邀请成员、改角色、启停账号；不能操作自己。

## 12. 系统日志（管理员）

**入口**：侧边栏 `ADMIN · 管理员` 分组下「系统日志」，路由 `/admin/logs`。

**界面上有什么**

- 顶部统计条：**全部 128 / 成功 119 / 警告 6 / 失败 3**，可点击筛选；
- 「导出日志」按钮；
- 表格列：**时间、用户、操作类型、结果、耗时、错误信息**；
- 底部分页（`共 128 条`）。

日志里记的不只是人的操作，还包括系统的动作，例如：

| 时间 | 用户 | 操作类型 | 耗时 | 错误信息 |
|---|---|---|---|---|
| 09:12:04 | — | 登录 | 318ms | — |
| 09:11:58 | 系统(调度器) | 执行模型调用 | 1,240ms | — |
| 09:08:45 | 系统(LLM 网关) | 接口重试 | 8,021ms | 429 rate limit，第 2/3 次重试 |
| 09:01:33 | 系统(评审模型) | 评审调用 | 30,000ms | timeout after 30000ms，已进入重试队列 |
| 08:46:19 | 陈默 | 调整用户角色 | 104ms | 账号已禁用（admin 手动停用） |
| 08:40:07 | — | 批量导入用例 | 1,560ms | 解析成功 18 条 / 失败 0 条 |
| 08:32:51 | 系统(收敛检测) | 迭代轮次完成 | 42ms | R03 最优 84.6，未触发收敛 |

**能做什么**

按结果筛选、导出、定位问题。

**作用**

**可追溯性**——这是「工程化」最不起眼但最关键的一环。

注意日志里**系统动作也被记录**（调度器、LLM 网关、评审模型、收敛检测），而且**耗时和错误原因都留痕**。
这带来一个很实际的能力：当迭代分数异常、任务中途失败时，不需要猜，可以直接看到——是模型调用超时了、被限流重试了、还是某一轮收敛检测判定不对。

配合任务详情里的「断点续跑」，系统具备了一个完整的自证能力：**出了问题能说清出在哪一步**。

## 13. 模块之间的关系（一张数据流看全）

```
登录 ──► 资产门户（看清家底：任务 / 版本 / 评测 / 知识库 / 端点 / 调用量）
              ▲
              │ 汇总
创建任务 ──► 任务详情（迭代看板）──► 报告 ──► 分享（免登录链接）
  │  目标 + 评分标准 + 用例集     │
  │                              ├── 人工抽检（校准自动评分）
  ├── 知识库（RAG 上下文注入）    │
  └── 模型评测（选执行模型）      └── 在线服务（把最优版本发布成接口）
                                     ▲
                    工作流（多步编排 + 步骤级优化）
                                     ▲
              用户管理 / 系统日志（管理支撑，全程留痕）
```

- **上游决定质量**：创建任务时的目标、评分标准、用例集，决定了整套优化的上限；
- **中游是引擎**：任务详情里的四步闭环（变体生成 → 执行 → 评估 → 择优）自动跑完；
- **下游产生价值**：报告交出去（分享）、提示词用起来（在线服务）、复杂任务拆开跑（工作流）；
- **两侧是保障**：知识库防幻觉、模型评测选型、人工抽检校准、系统日志追溯。

## 14. 发现的两个入口问题

解析过程中核对路由与导航时发现：**「工作流」和「分享中心」这两个页面在侧边栏没有入口。**

- 两个页面的路由、组件、接口调用都是完整的（`/workflows`、`/shares`），
  `MainLayout.tsx` 里甚至已经写了 `location.pathname.startsWith('/workflows')` 的高亮判断，
  但 `navBtn(...)` 里**没有对应的两个菜单项**——代码只处理了「进去以后怎么高亮」，没做「怎么进去」；
- 现状是只能手工在地址栏输入 URL 才能打开，演示时容易找不到页面。

**建议**：在侧边栏「知识库」之后补两项即可（图标可复用）：

```
{navBtn('workflows', <PartitionOutlined />, '工作流', '/workflows')}
{navBtn('shares', <ShareAltOutlined />, '分享中心', '/shares')}
```

顺带把 `selectedKey` 里缺的 `/shares` 分支补上（目前只有 `/workflows` 有），菜单高亮才完整。
